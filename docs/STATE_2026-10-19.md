写于技术栈转向立项前。只读核查 PezMax-One、PezMax-Go、Ncrust、arc-deck、Kanesumi 各扇区后的结论，
作为 `ARCHITECTURE.md` 与 `PLAN.md` 的事实底座。证据以 `仓库/路径` 标注；与源码冲突时以源码为准。

**判断**：可复用的是**知识**而不是代码——pdfium 渲染管线（网格 / 连续两种视图、后台渲染 + 磁盘缓存
`.cache/pdf/{file_id}/p{idx}_s{scale}.rgba`）、断点下载、缓存目录约定、Linux 全局菜单的协议细节。
egui 的单结构体 + 每帧重建模式不迁往任何新端。

**更新器的历史包袱**：1.0.0 的更新器请求 `/releases/latest`，Windows 端最后兜底「任意 `.msi`」
（`src/api/update.rs:160-188`）。改用 CrateStack 班次后 Latest 徽章指向的班次里不再有 `.msi`，
1.0.0 用户的应用内更新会报「release 中没有 Windows(.msi) 安装包」。处理方案见 `RELEASES.md` §迁移。

## 2. PezMax-Go：新后端，契约已换代

`Luminous` / `Lyohnyen` 分支），**本仓只消费它的 `/datum/*` 契约，不改它**。

| 项 | 现状 |
|---|---|
| 服务端 | Go / Gin（基于 GoAdmin），PostgreSQL 16 + Redis 7 + MinIO，LibreOffice 转档；Docker Compose 部署，可选 Nginx edge（下载分档限速） |
| 官方桌面端 | 同仓 `PezMax-Desktop/`：Electron 39 + Vue 3 + Element Plus，RuoYi 残留在清理中；更新走 electron-updater + `gh-proxy.com` 镜像 |
| 管理端 | Vben Admin（`k_admin/admin-web`），与桌面端身份体系隔离 |
| 契约文档 | Swagger：`k_admin/internal/kadmin/docs/swagger.json`，77 个 `/datum/*` 路径，另有 `/system/notification/user/{popup,scroll}`、`/system/config/login` |

### 契约要点（新客户端必须遵守）

- **信封**：JSON 一般为 `{code, data, message, msg}`，`code = 0` 为成功；列表为 RuoYi `TableDataInfo`
  形状 `{code, rows, total, msg}`，「存在不同的分页形状」（README §接口入口）。错误以**真实 HTTP 状态码**
  表达（Electron 侧已删除 in-body 401 双轨，`docs/pezmax-remaining-tasks.md` #6）。
- **会话**：`POST /datum/user/login`（`username / password / code / uuid`），返回 Redis 中的 opaque
  Bearer token，默认 120 小时；请求头 `Authorization: Bearer <token>`；HTTP 401 → 会话失效流程。
  桌面用户与管理员账号**不互通**。
- **验证码**：`GET /datum/user/captchaImage` → `{captchaEnabled, uuid, img}`，`img` 为**不带前缀的 base64 JPEG**。
- **分页**：`pageNum`/`page` + `pageSize`/`size`，默认 20，**单页上限 100**（`datum_file.go:268`）。
  需要全量时按 `total` 逐页拉（Electron `utils/pagination.js`）。
- **哈希缓存协议**（文件树、排行榜）：客户端带 `?hash=<上次的值>`；未变化时响应 `unchanged: true`
  且不带 payload，客户端沿用本地副本（`datum_file.go:29-195`）。
- **下载**：`GET /datum/download/file?fileId=` / `/datum/download/ebook?ebookId=`，会话鉴权、服务端落下载记录，
  支持 Range / ETag 断点续传；经 edge 时每 IP 1 个下载连接、按并发分档限速。
- **上传**：multipart，单文件默认 ≤ 200 MiB；白名单 DOC/DOCX/PPT/PPTX/PDF/JPG/PNG/WEBP/TXT/MD/EPUB/MOBI/AZW3；
  Office 转 PDF 存储；TXT/MD 必须 UTF-8；新上传进入**待审核**，审核后公开。
- **文件 URL**：存量数据里有内网 host（`localhost`/`127.0.0.1`/`minio`/`172.*`），Electron 用
  `normalizeFileUrl` 在客户端改写（`utils/url.js`）；上游计划在服务端修库后弃用客户端改写（next-tasks 任务四）。
- **通知**：5 类（1 版本更新 / 2 系统故障 / 3 系统维护 / 4 资料下架 / 5 公告），带发布窗口与故障 / 维护时间段；
  **已读状态只存客户端本地**（服务端无 per-user 已读模型）。

## 3. 可借鉴的兄弟工程

### Ncrust（`../Ncrust`）—— 本次转向的样板

- **monorepo + 平台目录**：Android `app/`、Windows `windows/`、跨端 `spec/`，各平台目录有自己的权威 `AGENTS.md`。
- **共享答案，不共享实现**（`spec/README.md`）：三端不共用代码，共用语言无关的夹具（JSON，带 `id` /
  `description` / `source`）；**先改 spec 再改实现**；各端测试按相对路径直接读 `spec/`，不复制。
- **CrateStack 滚动多平台班次**（`docs/RELEASES.md`）：tag `CrateStack-YYYYMMDD<A..Z>`，一班装载各平台最新资产，
  附机器可读 `manifest.json`（实物见 `CrateStack-20261015A`），资产名 `ncrust-[平台]-[架构]-[版本]`；
  应用内更新**按资产名跨班次找严格更高版本**、不看 Latest 徽章，规则由 `spec/fixtures/update/` 锁死。
- **Windows 端**（`windows/AGENTS.md`，M1 已日常可用）：UWP + WinUI 2.8 + .NET Native；`Ncrust.Core`
  为 netstandard2.0、不依赖 WinRT 与 UI、`dotnet test` 秒级跑；自研零反射 `JsonValue`；平台控件优先、
  `XamlControlsResources Version1` 直角样式、强调色跟随系统、Segoe MDL2 图标、`x:Bind` only、无 DI 框架；
  MSIX + `.appinstaller` + `.cer` 三件套发布；约 40 条「已知的坑」。
- **Android 端**：Kotlin + Compose，`includeBuild("../Kanesumi-sec-a")` composite build，零 material3。

### arc-deck（`../arc-deck`）

同一产品的 UWP 与 Rust 双实现。结论被 Ncrust 采纳：**UWP + WinUI 2 平台免费提供文本、IME、滚动、虚拟化、
无障碍**，自绘路线这些都要自己写。`uwp/tools/shot/`（截图 / UIA / 对比度 / 资源审计）是可移植的验证工具。

## 4. 结论

1. egui 版无法平滑升级到新契约：契约换代 + 单体结构，**重写各端、保留知识**是成本最低的路线。
2. Ncrust 的三件套——平台目录 monorepo、`spec/` 共享答案、CrateStack 班次——可以几乎原样套用；
   PezMax 的业务逻辑是 REST CRUD + 少量协议（哈希缓存、分页、续传、URL 归一、更新），比 Ncrust 的加密协议更简单，
   「不做共享核心库」的理由在这里更成立。
3. 新增的阅读需求（PDF / EPUB / Markdown / 图片）是三端差异最大的地方：Windows 有 `Windows.Data.Pdf` 与 WebView2，
   Android 有 `PdfRenderer`，Linux 只能靠 pdfium + Kanesumi 自绘，EPUB 在 Linux 上没有现成渲染器。这是 M0 要先验的风险。
